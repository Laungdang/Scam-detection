## Quick card (อ่าน 5 นาทีก่อน label — รายละเอียดอยู่ในข้อ 0-7)

1. **คำถามเดียว:** ถ้าทำตามข้อความนี้ ฉันจะเสียอะไร (เงิน / ข้อมูล-รหัส / การควบคุมเครื่อง)? — คำว่า "ด่วน", ชื่อธนาคาร, "ฟรี", "ราคาถูก" ไม่ใช่หลักฐาน
2. **ไม่มีการขอเลย → `safe`** ยกเว้น opener 4 แบบ → `caution`: เปลี่ยนเบอร์ใหม่ · ทักผิด/อยากรู้จัก · ข้อเสนอการเงินเกินจริง · แจ้งว่าได้รางวัล/วงเงิน
3. **มีการขอ + สัญญาณชัดในข้อความ → `danger`** — สัญญาณโดยลำพัง: ขอ OTP/รหัส · บัญชีคนอื่น/ชื่อไม่ตรง · ห้ามบอกใคร · จ่ายก่อนเพื่อได้งาน/รางวัล; สัญญาณแบบประกอบ: ขู่คดี+ให้แก้ · อ้างหน่วยงาน+ลิงก์/บัญชีบุคคล · กรอกข้อมูลผ่านลิงก์เพื่อรับสิทธิ์/รางวัล (แม้ไม่เห็น URL — v1.2) · opener+ช่องทาง · ID ภายนอก+ขอเงิน (รายการเต็มขั้น 2)
4. **มีการขอ แต่ไม่มีสัญญาณชัด → `caution`** — "โอนก่อน/มัดจำ/เหลือชิ้นเดียว/ทัก DM/หมดสิทธิ์/ราคาพิเศษถึงวันนี้" **ไม่ใช่สัญญาณ** (คนขายจริงก็ใช้)
5. **ข้อเท็จจริงชี้ขาดไม่อยู่ในข้อความ → `caution` + `needs_info`** จากรายการปิด: `url` (เฉพาะลิงก์ที่ไม่ผูกกับการขอข้อมูล/เงิน) · `sender_identity` · `seller_identity` · `platform_policy` · `seller_reputation` · `verify_with_claimed_person` · `account_name_match`
6. **ทิศทางเงิน:** ผู้ซื้อขอเลขบัญชี*ผู้ขาย*เพื่อจ่ายให้ = ผู้รับไม่เสียอะไร → `safe`
7. **คำอ้าง ≠ บริบท:** "รุ่นพี่ฝากบอก / แอดมิน / แม่ / แฟนเรา" ตรวจไม่ได้ → ไม่ยก danger แต่ก็ไม่ให้ safe (→ `caution` + needs_info) ยกเว้น "บัญชีนี้ของแฟน/คนอื่น" = บัญชีม้า → `danger`
8. **ข้อความเล่าเหตุการณ์** ("มีคนขอ… บอกว่าเป็น…") → ตัดสิน *สิ่งที่ถูกเล่า* บันทึก `input_form: narrative`
9. **ห้าม:** danger เพราะ "ดูเหมือน SMS/มีลิงก์" · safe เพราะ "ภาษาสุภาพ" · category `other` ถ้าเข้าหมวดอื่นได้
10. **ก่อน label:** cluster ข้อความที่ต่างแค่ emoji/typo/ตัวยืด แล้วตัดสินทั้ง cluster ครั้งเดียว; A2 ตอบจาก blind sheet (`data/annotation/v1.1_calibration_blind.csv`) ก่อนอ่านตาราง 1.2

## 0. หลักคิดสำคัญที่สุด

**ตัดสินจาก "การขอ" ไม่ใช่จาก "คำ"**

ข้อความ scam เกือบทั้งหมดต้องการให้เหยื่อ **ทำอะไรบางอย่าง**: โอนเงิน, ให้ข้อมูล/รหัส, กดลิงก์/ติดตั้งแอป, หรือย้ายไปคุยช่องทางที่ควบคุมได้ ข้อความที่ไม่มีการขอใดๆ เลย **แทบไม่มีทางเป็น danger** ต่อให้มีคำว่า "ด่วน", "ธนาคาร", "ฟรี"

คำเร่งด่วน / ชื่อธนาคาร / คำว่าฟรี พบในข้อความปกติตลอด (flash sale, อาจารย์ทวงงาน, แม่ขอเงินค่าเทอม, SMS แจ้งยอดจากธนาคารจริง) — annotator ต้องอ่านทั้งข้อความแล้วถามว่า **"ถ้าทำตามข้อความนี้ ฉันจะเสียอะไร"**

หลักคิดเพิ่มใน v1.1 (ทั้งหมดเป็นผลสืบเนื่องจากคำถามเดียวกัน):

- **ทิศทางของการขอสำคัญ** — "ขอเลขบัญชีของคุณ เดี๋ยวโอนให้" คือผู้ถามเป็นฝ่ายจ่าย ผู้รับไม่เสียอะไร → ไม่ใช่ "การขอ" ตามข้อ 0 (ตัดสิน Q3) ต่างจาก "ขอ OTP/รหัส" ที่ผู้รับเสีย credential
- **คำอ้างในข้อความ ≠ บริบทที่ตรวจได้** — "รุ่นพี่ฝากบอก", "แอดมินคณะ", "บัญชีแฟนเราเอง" เป็น *คำอ้าง* (pretext) ไม่ใช่หลักฐานว่าชอบธรรม บริบทชอบธรรมต้องมาจากสิ่งที่ผู้รับ **ยืนยันได้ก่อนเสียเงิน/ข้อมูล** (metadata, คำยืนยันของผู้ใช้, หรือขั้นตอนที่ต้องพบตัวจริงก่อนจ่าย — ข้อ 1.1 ขั้น 3) และคำอ้างก็ **ไม่ใช่สัญญาณหลอกโดยตัวเอง** — ผลของมันคือทำให้ "ตรวจไม่ได้" (Q7 → caution ไม่ใช่ danger) ยกเว้น "บัญชีนี้ของแฟน/คนอื่น" ซึ่งเป็นการยอมรับเองว่าปลายทางเป็นบุคคลที่สาม = สัญญาณ (Q2)
- **ข้อมูลไม่พอ ≠ ปลอดภัย และ ≠ อันตราย** — ถ้าข้อเท็จจริงที่ชี้ขาด (URL จริง, ตัวตนผู้ส่ง, กฎของแพลตฟอร์ม, คนรู้จักจริงไหม) ไม่อยู่ในข้อความ ให้ `caution` + `needs_info` (ข้อ 1.3) ไม่เดาเป็น safe หรือ danger
- **ข้อความเล่าเหตุการณ์ → ตัดสินสิ่งที่ถูกเล่า** — "มีคนขอรหัส บอกว่าเป็นแอดมิน" ไม่ได้ขออะไรจากผู้อ่าน แต่ *เหตุการณ์ที่เล่า* มีการขอ ให้ประเมินการขอนั้น (ข้อ 1.4, ตัดสิน Q4)

หลักนี้สอดคล้องกับ CLAUDE.md 5.2/6.8: มิติใน lexicon เป็น *ข้อเท็จจริง* ที่พบในข้อความ ผู้ตัดสิน (annotator ที่นี่ / Claude ใน Q&A) เป็นคนชั่งว่าการขอ + สัญญาณ co-occur หรือไม่ — ไม่มีมิติใดมี weight

## 1. Verdict (บังคับทุก record tier A/S — tier N ดูข้อ 4)

| verdict | นิยาม | เกณฑ์ตัดสิน |
|---|---|---|
| `danger` | ข้อความนี้ **มีเจตนาหลอก** ให้เสียเงิน/ข้อมูล/การควบคุมอุปกรณ์ | มี "การขอ" (ข้อ 0) **และ** มีสัญญาณหลอกในรายการขั้น 2 อย่างน้อย 1 อย่าง *ที่ข้อความระบุองค์ประกอบครบ* (ข้อ 1.1, ข้อ 3) **และ** ไม่มีบริบทชอบธรรม *ที่ตรวจได้* |
| `caution` | ไม่แน่ใจว่าหลอก แต่ **ถ้าทำตามโดยไม่ตรวจสอบก่อน มีความเสี่ยง** | (ก) มี "การขอ" แต่สัญญาณหลอกอ่อน/ก้ำกึ่ง; (ข) เป็น opener ของ scam pattern ที่รู้จัก ที่ยังไม่ขออะไร (รายการปิด 4 แบบ — 1.1.1 เช่น "เปลี่ยนเบอร์ใหม่นะ", "คุณได้รับวงเงิน 200,000"); (ค) ข้อเท็จจริงชี้ขาดไม่อยู่ในข้อความ → บันทึก `needs_info` (ข้อ 1.3) |
| `safe` | ไม่มีสัญญาณหลอก | ไม่มี "การขอ" (และไม่ใช่ opener ตาม 1.1 ขั้น 1), หรือมีการขอแต่บริบทชอบธรรมชัดเจนและตรวจได้ (เพื่อนขอค่าข้าวคืน — *มี metadata ยืนยันผู้ส่ง*, ธนาคารแจ้งยอด, ผู้ซื้อขอเลขบัญชีผู้ขายเพื่อจ่ายให้) |

**ข้อห้าม:**
- ห้ามให้ `danger` เพราะ "ดูเหมือน SMS" หรือ "มีลิงก์" อย่างเดียว — SMS ธนาคารจริงก็มีลิงก์; ลิงก์แปลก (shortener/TLD แปลก) ในข้อความที่ไม่ขออะไรอื่น → caution (§7 #3) ไม่ใช่ danger
- ห้ามให้ `danger` เพราะ "เร่ง/ของเหลือน้อย/ราคาพิเศษถึงวันนี้" + "โอนก่อน" จากผู้ขายที่ไม่รู้จัก โดยไม่มีสัญญาณอื่น — แพลตฟอร์มหลายแห่งให้จ่ายก่อนเป็นปกติ (ตัดสิน Q1, Q6 → caution)
- ห้ามให้ `safe` เพราะ "ภาษาสุภาพ" — scam ส่วนใหญ่ภาษาสุภาพมาก
- ห้ามให้ `safe` เพราะข้อความ *อ้าง* ว่าเป็นคนรู้จัก/มีบทบาท (รุ่นพี่, แอดมิน, แฟน, ฝากบอก) — คำอ้างไม่ใช่บริบทที่ตรวจได้ (ตัดสิน Q7 → caution + needs_info)
- ไม่มี `uncertain` ใน label — ถ้าไม่แน่ใจเพราะ *ตัวเอง* ชั่งไม่ออก → `caution` + `confidence` ต่ำ (ข้อ 5); ถ้าไม่แน่ใจเพราะ *ข้อมูลไม่อยู่ในข้อความ* → `caution` + `needs_info` (ข้อ 1.3) — สองกรณีนี้ต้องแยกกันให้ชัด

### 1.1 Decision procedure (ทำตามลำดับ)

```
0. ข้อความนี้เป็น "ข้อความที่ส่งถึงผู้รับ" หรือ "คำบอกเล่าเหตุการณ์"? (ข้อ 1.4)
   narrative = ผู้เขียนเล่าว่ามี "บุคคลที่สาม" ขอ/ทำอะไรกับผู้เขียน **และ** ไม่ได้สั่ง/ชวนผู้อ่านให้ทำ
   ("มีคนขอ…", "อ้างว่าเป็น…", "บอกว่าเป็น…", "โดนทัก…", "เพื่อนเจอแบบนี้…")
   direct = ประโยคที่สั่ง/ชวน/ส่งต่อคำสั่งถึงผู้อ่าน แม้จะสั้น ไม่มีประธาน หรือมีคำกันเหนียว
   ("โอนมาเลย", "ทักไลน์อย่างเดียวคับ", "รุ่นพี่ฝากบอกให้โอน…", "มีลิงก์ให้กรอก… ลองเช็คก่อนนะ")
   → narrative ....... บันทึก input_form: "narrative" แล้วประเมิน "การขอที่ถูกเล่า"
                       ตามขั้น 1-5 เสมือนผู้เล่าเป็นผู้รับ (verdict เป็นของเหตุการณ์)
   → direct .......... input_form: "direct" ไปขั้น 1

1. ข้อความนี้ขอให้ผู้รับทำอะไรที่ทำให้ผู้รับ "เสีย" ไหม?
   (โอน/จ่าย/มัดจำ, ให้ข้อมูล/รหัส/OTP/"ยืนยันข้อมูล-ตัวตน", กดลิงก์/ติดตั้ง, แอดไลน์/Telegram/ย้ายไปช่องทางภายนอก,
    โทรกลับเบอร์ที่ให้, ติดต่อเพื่อรับข้อเสนอที่ระบุเงื่อนไข)
   นับเป็นการขอเสมอ (แม้คลุมเครือ):
     - "ยืนยันข้อมูล / ยืนยันตัวตน / ส่งรหัส" แม้ไม่ระบุว่าอะไรและไม่ระบุช่องทาง — ผู้รับเสีย credential
       (B3: ถ้าไม่มีช่องทาง → ไม่ใช่สัญญาณขั้น 2 → ไปขั้น 4)
     - อ้างถึงลิงก์/แอป/บัญชีที่ "มีอยู่" แต่ไม่แสดงค่าในข้อความ ("มีลิงก์ให้กรอก…", "โอนมาบัญชีนี้")
       = การขอที่ระบุช่องทางแล้ว ไม่ใช่ CTA ลอย (Q5)
   ไม่นับเป็นการขอ:
     - ขอเลขบัญชี/พร้อมเพย์ "ของผู้รับ" เพื่อโอนเงิน "ให้" ผู้รับ (ผู้ซื้อถามผู้ขาย) — Q3
     - call-to-action ลอย ๆ ที่วัตถุคือ ซื้อ/จอง/สมัคร/ลงทะเบียน (ผู้รับไม่เสียเงิน/ข้อมูลจากการทำ CTA นั้นเอง)
       และไม่ระบุช่องทาง ลิงก์ เบอร์ บัญชี หรือข้อมูล — A2
       (ขอบเขต: "จองภายในวันนี้" = ไม่ใช่การขอ; "ยืนยันข้อมูลภายในวันนี้" = การขอ ตามข้อข้างบน)
     - "ทัก DM / inbox ได้ / ส่งในกลุ่มได้เลย" บนแพลตฟอร์มเดิม โดยข้อความไม่มีข้อเสนอ/เงื่อนไขให้ทำตาม — B7
       (DM ไม่ใช่สัญญาณขั้น 2 — ผลเดียวของมันคือทำให้ "ข้อเสนอที่ระบุเงื่อนไข" กลายเป็นการขอ; §7 #15/#16)
     - contact handle ที่ผู้โพสต์แนบมาเองใน "โพสต์กระจาย" ที่ไม่มีคำขอเจาะจงผู้รับ ("มีใครขาย… line: @id") — B9
   → ไม่มีเลย ......................................... safe
     ยกเว้น opener ของ scam pattern ที่รู้จัก (รายการปิด 4 แบบ — ดู 1.1.1):
       (1) "เปลี่ยนเบอร์ใหม่"   (2) ทักผิด-อยากรู้จักจากคนแปลกหน้า
       (3) ข้อเสนอทางการเงินเกินจริง (รายได้/ผลตอบแทนเกินจริง, กู้ไม่ต้องค้ำ/อนุมัติทันที — เกณฑ์ §3 financial_offer)
       (4) แจ้งว่าได้รางวัล/วงเงิน/เงินคืน/สิทธิ์พิเศษ โดยยังไม่บอกช่องทางรับ
     → caution (category ตามข้อ 2)
```

#### 1.1.1 ทำไมขั้น 1 "ไม่มีการขอ → safe" จึงมีข้อยกเว้น (แก้ความขัดแย้ง v1.0)

v1.0 ขั้น 1 บอกว่า "ไม่มีการขอ → safe" แต่ calibration ("เปลี่ยนเบอร์ใหม่นะ", LinkedIn opener) และ §7 #4 ให้ caution กับข้อความที่ยังไม่ขออะไร — v1.1 ตัดสินว่า **ข้อยกเว้น (caution) ชนะ** ด้วยเหตุผล:

1. opener เหล่านี้คือ *turn แรก* ของ scam หลาย turn — สิ่งที่มันขอจริงคือ "ตอบกลับ/เซฟเบอร์/คุยต่อ" ซึ่งเป็นการเตรียมการขอในรอบถัดไป คำถาม §0 "ถ้าทำตามฉันจะเสียอะไร" ตอบว่า "เสียโอกาสตรวจสอบก่อนที่เขาจะขอเงิน"
2. `caution` เป็น *severity* ("ระวังแค่ไหน") ไม่ใช่ class — ข้อความที่ควร "ตรวจสอบก่อนตอบ" คือ caution ตามนิยาม
3. ข้อยกเว้นเป็น **รายการปิด 4 แบบ**: (1) เปลี่ยนเบอร์ (2) ทักผิด-อยากรู้จัก (3) ข้อเสนอทางการเงินเกินจริง — รายได้/ผลตอบแทนเกินจริง, กู้ไม่ต้องค้ำ/อนุมัติทันที ตามเกณฑ์ §3 financial_offer (4) แจ้งว่าได้รางวัล/วงเงิน/เงินคืน/สิทธิ์พิเศษ โดยยังไม่บอกช่องทางรับ — ข้อความไม่มีการขออื่นใดยังคง safe ตามขั้น 1 ไม่ให้ข้อยกเว้นกลืนกฎหลัก การเพิ่มแบบใหม่เข้ารายการต้อง bump version (แบบ (4) และการขยาย (3) ให้ครอบกู้ เพิ่มตอน finalize v1.1 เพื่อแก้แถว "วงเงินกู้จาก ธปท." ที่เดิมให้ danger ทั้งที่ไม่มีการขอ และ "สินเชื่อ ไม่ต้องค้ำ" ที่ procedure เดิมให้ safe — review consistency)
4. opener ทุกแบบในรายการปิด **+ ช่องทางใด ๆ** (inbox/DM/LINE/ลิงก์/เบอร์) = การขอ (ขั้น 1) + สัญญาณ (j) (ขั้น 2) → danger — นี่คือเหตุผล *เดียว* ที่ "ทัก DM" เปลี่ยน verdict ได้ (§7 #15) ส่วน โอนก่อน/มัดจำ + DM ยังเป็น caution เพราะโอนก่อนไม่ใช่สัญญาณ (§7 #8)

### 1.3 ข้อมูลไม่พอ (`needs_info`) — ใหม่ใน v1.1

ใช้เมื่อ **ข้อเท็จจริงที่จะชี้ขาด verdict ไม่อยู่ในข้อความ** และ annotator ไม่มี metadata มาเติม — verdict = `caution` เสมอ และบันทึกว่าขาดอะไรจากรายการปิดนี้:

| ค่า | หมายถึง | ตัวอย่างข้อความ |
|---|---|---|
| `url` | ข้อความพูดถึงลิงก์/ช่องทางที่ไม่แสดง **และลิงก์นั้นไม่ได้ผูกกับการขอข้อมูล/เงินเพื่อรับสิทธิ์** — ไม่มี URL ให้ประเมินโดเมน/shortener/TLD (URL ที่มีแต่เป็น shortener = *มี* URL → ไม่ใช้ค่านี้ ดู C39; "ลิงก์ให้กรอกข้อมูลเพื่อรับสิทธิ์" = สัญญาณ (f) ครบแล้ว → danger ไม่ใช้ค่านี้ — v1.2, C38) | "มีลิงก์รายละเอียดกิจกรรม ลองดูนะ" (C38b), "ระบบแจ้งให้ยืนยันข้อมูลบางอย่าง" (B3 — ไม่มีรางวัล/สิทธิ์ผูก) |
| `sender_identity` | ไม่รู้ว่าใครส่ง หรือผู้ส่งอ้างบทบาท/ความสัมพันธ์ที่ตรวจไม่ได้ | "ระบบแจ้งให้ยืนยันข้อมูลภายในวันนี้", "รุ่นพี่ฝากบอก…" (Q7) |
| `seller_identity` | ผู้ขาย P2P ไม่ระบุร้าน/ตัวตน/ประวัติ | "รีบโอนก่อนนะ เหลือคนเดียวแล้ว" (Q6) |
| `platform_policy` | ไม่รู้ว่าแพลตฟอร์ม/ร้านมีกฎให้จ่ายก่อน หรือมีระบบคุ้มครองผู้ซื้อไหม | "โอนก่อนส่งเท่านั้น" (Q1, Q6) |
| `seller_reputation` | ไม่รู้ว่าผู้ขาย/ผู้โพสต์มีเครดิตในกลุ่มไหม — เคยมีคนในกลุ่มซื้อ/ยืนยัน, รีวิว, ประวัติการขาย (v1.3 — จากเหตุผลของ A2 ใน Q1/Q6: "เช็คเครดิตพ่อค้าในกลุ่ม / มีคนในกลุ่มยืนยันไหม") — ต่างจาก `seller_identity` (ตัวตน) ตรงที่เป็น *ประวัติ* ซึ่งคนอื่นในกลุ่มตอบได้ | "รีบโอนก่อนนะ เหลือคนเดียวแล้ว ทัก DM" (Q6), "ของอยู่ต่างจังหวัด โอนก่อนส่งเท่านั้น" (Q1) |
| `verify_with_claimed_person` | ต้องยืนยันกับคนที่ถูกอ้างถึง (รุ่นพี่, แม่, แอดมิน) ผ่านช่องทางเดิมที่รู้จัก | "รุ่นพี่ฝากบอกให้โอนค่าชีท" (Q7) |
| `account_name_match` | ต้องเช็คว่าชื่อบัญชีปลายทางตรงกับผู้ขาย/ผู้ที่อ้างไหม — ใช้เฉพาะเมื่อข้อความ **ระบุบัญชีปลายทาง** แต่ยังไม่เห็นชื่อ | "โอนมาบัญชีนี้ xxx-x-xx5678" ที่ยังไม่เห็นชื่อ; ถ้าเห็นแล้วไม่ตรง **หรือผู้ส่งบอกเองว่าเป็นบัญชีคนอื่น** (แฟน/ญาติ/เพื่อน) → danger ตาม Q2 ไม่ใช่ needs_info |

**กฎ:**
- **`sender_identity` vs `verify_with_claimed_person`:** `sender_identity` = ไม่รู้ว่าตัวผู้ส่งเองเป็นใคร; `verify_with_claimed_person` = ข้อความอ้างถึงบุคคลที่สาม (รุ่นพี่, แม่, แอดมิน) ที่ต้องไปถาม; ใส่ **ทั้งคู่** เมื่อผู้ส่งอ้างว่าส่งต่อแทนบุคคลที่สาม ("รุ่นพี่ฝากบอก" — C35); ใส่ **เฉพาะ** verify_with_claimed_person เมื่อผู้ส่งอ้างว่าเป็นบุคคลนั้นเอง ("แม่โอนค่าเทอม" — C05); ห้ามใส่ sender_identity เมื่อสัญญาณโดยลำพัง (a)/(b) ทำให้ตัวตนผู้ส่งไม่เปลี่ยน verdict (C33)
- **ชุดค่ามาตรฐานต่อเคส** (ให้ % agreement ของ needs_info วัดได้): marketplace โอนก่อน/มัดจำ ไม่มี metadata → `[seller_identity, platform_policy, seller_reputation]` (ไม่ใส่ account_name_match ถ้าข้อความไม่ระบุบัญชี); ลิงก์ที่มองไม่เห็น → `[url]`; ขอข้อมูลคลุมเครือไม่มีผู้ส่ง/ช่องทาง → `[sender_identity, url]`
- `needs_info` ใช้คู่กับ `caution` เท่านั้น — ห้ามใช้กับ `safe` (safe ต้องไม่มีอะไรค้าง) และห้ามใช้เพื่อเลี่ยง `danger` เมื่อสัญญาณหลอกชัดแล้ว (เช่น Q2 บัญชีแฟน, แอดมินคณะ + พร้อมเพย์บุคคล) — ข้อมูลเพิ่มอาจเปลี่ยน verdict ใน turn ถัดไปของ Q&A ได้ แต่ verdict ของ *ข้อความนี้* คือ danger
- ต้องเลือกจากรายการปิดข้างบน — ค่าใหม่ต้อง bump version; ห้ามใส่ค่า PII ลงใน needs_info
- ใส่เฉพาะสิ่งที่ *ถ้ารู้แล้วจะเปลี่ยน verdict ได้* ไม่ใช่ทุกอย่างที่ไม่รู้
- **นัยต่อ Q&A mode:** เมื่อ evidence ตรงกับกรณี needs_info ระบบต้องให้ verdict `caution` ของ turn นั้น และใช้ field `follow_up` ถามผู้ใช้ต่อเป็นคำถามเจาะจง (เช่น "ลิงก์เต็มคืออะไร", "รู้จักผู้ขายคนนี้มาก่อนไหม", "ลองถามรุ่นพี่คนนั้นตรงๆ ผ่านช่องทางเดิมว่าฝากบอกจริงไหม") แทนประโยคปิดทั่วไป

### 1.4 ข้อความเล่าเหตุการณ์ (`input_form: narrative`) — ขั้น 0

- **นิยาม (positive test):** narrative = ผู้เขียนเล่าว่ามี **บุคคลที่สาม** ขอ/ทำอะไรกับผู้เขียน ("มีคน…", "อ้างว่าเป็น…", "บอกว่าเป็น…", "โดนทัก…", "เจอแบบนี้ควรทำไง") **และ** ไม่ได้สั่ง/ชวนผู้อ่านให้ทำ; การส่งต่อคำสั่ง ("รุ่นพี่ฝากบอกให้โอน…" — C35) และการชวน ("มีลิงก์ให้กรอก… ลองเช็คก่อนนะ" — C38) = direct — ตัวแยกคือ "ผู้อ่านถูกขอให้ทำไหม" ไม่ใช่คำใดคำหนึ่ง; input_form ไม่กระทบ κ แต่กระทบ tier (ข้อ 4) จึงต้องตรงกัน
- **วิธีตัดสิน (ตัดสิน Q4):** ประเมิน "การขอที่ถูกเล่า" ตามขั้น 1-5 เสมือนผู้เล่าเป็นผู้รับ — verdict/category เป็นของ *เหตุการณ์* ไม่ใช่ของตัวข้อความ บันทึก `input_form: "narrative"` ให้ชัด
- ประโยคที่ **สั่ง** ผู้รับ ("ทักไลน์อย่างเดียวคับ", "โอนมาเลย") เป็น direct ไม่ใช่ narrative แม้จะสั้นหรือไม่มีประธาน (A11)
- คำกันเหนียว/hedge ("ลองเช็คก่อนนะ", "ระวังนะ", "ไม่แน่ใจ") **ไม่มีน้ำหนัก** ต่อ verdict ไม่ว่าจะอยู่ใน narrative หรือ direct — ตัดสินจากการขอ (ที่ถูกเล่า/ที่ถูกส่งต่อ) เท่านั้น และ hedge ไม่ใช่ตัวชี้ input_form (B6; C38 เป็น direct)
- **ผลต่อ tier (ตาม CLAUDE.md 10.2):** record ใน corpus tier A/S ที่เป็น narrative ให้ย้ายเป็น tier N (ข้อ 4) — ยังเก็บ verdict ของเหตุการณ์ไว้ใช้กับ RAG/Q&A eval แต่ห้ามเข้า train/test ของ ML (model จะเรียน "ข้อความพูดถึง scam" แทน scam) — ข้อนี้ไม่ใช้กับ external eval set (Kaggle-TU) ซึ่งไม่ใช่ corpus ของเรา

## 2. Category (บังคับเมื่อ verdict ≠ safe; `null` เมื่อ safe)

เลือก **1 หมวดหลัก** ตาม "กลไกหลอกหลัก" ไม่ใช่ตามช่องทาง ถ้าหลายหมวดซ้อน ใช้ลำดับความสำคัญ: กลไกที่ทำให้เหยื่อเสียเงิน/ข้อมูลโดยตรง > กลไกเปิด

| category | นิยาม | ตัวอย่าง | **ไม่ใช่** |
|---|---|---|---|
| `phishing_link` (= credential theft ทุกช่องทาง — ชื่อคงไว้เพื่อ compat กับ v1.0) | หลอกให้กดลิงก์/ติดตั้งแอป **หรือส่งรหัส/OTP ผ่านแชท** เพื่อขโมย credential/ข้อมูล หรือควบคุมเครื่อง — การขโมย credential คือกลไกหลัก; การขอ OTP/รหัสผ่านทางแชทอยู่หมวดนี้ **เสมอ** ห้ามลงไป other | "บัญชีถูกระงับ ยืนยันที่ลิงก์", "พัสดุตกค้าง คลิกอัปเดตที่อยู่", "อัปเดตแอปธนาคารที่ <URL>", "แอดมินกลุ่มขอรหัสยืนยัน" (Q4) | ข้อความที่มีลิงก์แต่กลไกหลักคืออย่างอื่น (เช่น ลงทุน → `investment_scam`) |
| `impersonation_authority` | อ้างเป็นเจ้าหน้าที่รัฐ/ตำรวจ/ศาล/สรรพากร/ธนาคาร แล้ว **ขู่** ให้ทำตาม โดยไม่ต้องพึ่งลิงก์ | "คุณมีคดีฟอกเงิน ติดต่อ DSI ที่เบอร์...", "สรรพากรแจ้งภาษีค้าง", call-center scam | อ้างธนาคาร + ลิงก์ (→ `phishing_link`); อ้างบทบาทในสถาบันเพื่อเก็บค่าธรรมเนียม (→ `financial_fraud`) |
| `financial_fraud` | หลอกว่ามีธุรกรรม/หนี้/ค่าใช้จ่าย/ค่าธรรมเนียมที่ต้อง **โอนเงิน/จ่าย** โดยตรง รวม advance fee และ marketplace ที่รับเงินแล้วไม่ส่ง | "เงินถูกถอน 50,000 โทรกลับ", ค่าไฟค้าง, หลอกซื้อของแล้วไม่ส่ง, **ค่าชีท/ค่าจองสิทธิ์/ค่ากิจกรรมปลอมจากผู้อ้างเป็นรุ่นพี่-แอดมิน, งานที่ต้องจ่ายค่าสมัครก่อน, บัญชีม้าอ้างเป็นของแฟน-ญาติ** (B10, Q2) — *หมวดไม่ได้บอก verdict*: เคสค่าชีท/ค่าจองจากผู้อ้างรุ่นพี่ที่ไม่มีปลายทางไม่ทางการเป็น caution ตาม §1.1 (C35) | ขู่คดี (→ impersonation), ลิงก์ (→ phishing); งานจ่ายค่าสมัครก่อน **ยังคง** financial_fraud แม้มีข้อเสนอรายได้เกินจริงร่วม เพราะกลไกคือเรียกเก็บเงินก่อน |
| `prize_scam` | ล่อว่าได้รางวัล/เงินคืน/สิทธิ์พิเศษ แล้วขอค่าธรรมเนียม/ข้อมูล/กดลิงก์ | "ผู้โชคดีได้ iPhone", "รับเงินคืนค่าไฟ", "เงินเยียวยาจากรัฐบาล กดลงทะเบียน" | โปรโมชั่นจริงที่ไม่ขออะไร (safe) |
| `loan_offer` | เสนอเงินกู้ที่ไม่มีจริง (ไม่ต้องค้ำ อนุมัติไว) เพื่อเก็บค่าธรรมเนียมล่วงหน้า/ข้อมูล | "สินเชื่อ 200,000 ไม่ต้องค้ำ", "อนุมัติใน 5 นาที แอดไลน์" | ล่อว่า "ได้รับ" วงเงินเป็นรางวัล (→ prize_scam ถ้ากลไกคือรางวัล) |
| `investment_scam` | ชวนลงทุน/เทรด/งานออนไลน์ ผลตอบแทน/รายได้เกินจริง โดยไม่เรียกเก็บเงินก่อน | "หุ้น VIP 30%/เดือน", "กดไลค์ได้เงิน", "Forex รับประกันกำไร", "งานออนไลน์วันละ 10,000 inbox ได้" | สินเชื่อ (→ loan_offer); ต้องจ่ายค่าสมัครก่อน (→ financial_fraud) |
| `romance_scam` | สร้างความสัมพันธ์/ทักผิด/ขอเป็นเพื่อน เพื่อขอเงินภายหลัง | "ทักผิดหรือเปล่า อยากรู้จัก", "ที่รัก ฉันติดที่ศุลกากร ช่วยโอน..." | อ้างเป็นคนรู้จักเดิม (→ borrowing_scam) |
| `borrowing_scam` | อ้างเป็นญาติ/เพื่อน/หลาน (มักบอกเปลี่ยนเบอร์) ขอยืมเงินฉุกเฉิน | "แม่ เปลี่ยนเบอร์นะ ขอยืม 5,000", "หลานประสบอุบัติเหตุ" | คนแปลกหน้าสร้างความสัมพันธ์ใหม่ (→ romance_scam); อ้างรุ่นพี่/แอดมินเก็บค่าธรรมเนียม (→ financial_fraud) |
| `other` | scam ชัดเจนที่เข้าไม่ได้สักหมวด **หรือ** caution กรณี A11 เท่านั้น (สั่งให้ย้ายช่องทางอย่างเดียว ± ID ภายนอก กลไกยังไม่ปรากฏ) | "ทักไลน์อย่างเดียวคับ ไม่ค่อยตอบในกลุ่ม" ± line: @id (C31/C32) | **ห้ามใช้เป็นถังขยะ** — ถ้าเข้าได้ ≥ 1 หมวด ห้ามเลือก other; ถ้าไม่ใช่ scam ให้ verdict=safe ไม่ใช่ other |

**บทเรียนจาก v1 (Week 4):** 44% ของ error มาจาก label `other` ที่จริงๆ เป็น `phishing_link` หรือ `safe` — ห้ามซ้ำ ถ้าเลือก other ต้องเขียนเหตุผลใน `annotator_notes`

**category ของ `caution` (เพิ่ม v1.1):** caution ก็ต้องมี category — เลือกหมวดของ pattern ที่ข้อความนี้เป็น *ขั้นแรก/opener* (เปลี่ยนเบอร์ → borrowing_scam, โอนก่อนส่ง → financial_fraud, พูดถึงลิงก์เก็บข้อมูล → phishing_link) ยกเว้นกรณีเดียวที่อนุญาต `other`: caution เพราะให้ย้ายช่องทางอย่างเดียว (± ID ภายนอก) และกลไกยังไม่ปรากฏ ("ทักไลน์อย่างเดียวคับ" ± line: @id — C31/C32) — ต้องมี notes และแยกนับใน error analysis (A11); category ของ opener รายการปิด: (1) → borrowing_scam, (2) → romance_scam, (3) รายได้เกินจริง → investment_scam / กู้ไม่ต้องค้ำ → loan_offer, (4) แจ้งได้รางวัล/วงเงิน → prize_scam

**Mapping กันสับสน (B10):** ค่าชีท/ค่าจองสิทธิ์/ค่ากิจกรรมปลอม, ค่าสมัครงาน, มัดจำสินค้าจากผู้ขายไม่รู้จัก → `financial_fraud`; Kaggle-TU ให้ other/investment_scam ในกลุ่มนี้ = label noise ที่ต้องแยกออกตอนเทียบ category

## 3. สัญญาณหลอก (อ้างอิง 14 มิติใน `data/lexicon/scam_lexicon.yaml` v1.1)

ใช้เป็น checklist ช่วยดู — **ไม่ใช่** นับจำนวนแล้วตัดสิน (ไฟล์ lexicon ไม่มี weight/verdict โดยเจตนา — CLAUDE.md 6.8) มิติ `amount_mention` และ `refuse_verification` เพิ่มจาก 12 มิติเดิมหลัง Kaggle-TU รอบ 2 — ไฟล์ lexicon ต้อง bump `version` เป็น `"1.1"` พร้อม guideline นี้ (ตอนนี้ไฟล์ยังเขียน 1.0 ทั้งที่มี 14 มิติ) และคำที่ guideline นี้พึ่งพา (หมดสิทธิ์ → urgency, "ฝากบอก"/"รุ่นพี่" → borrowing_pretext, regex บัญชีบุคคลที่สาม → money_request) ต้องอยู่ในมิติที่ตรงกับตารางข้างล่าง ไม่งั้น evidence ที่ Claude เห็นจะสวนทางกับ guideline (review system-alignment)

การอ่านตาราง: คอลัมน์ "บ่งชี้หลอกเมื่อ" คือเงื่อนไขที่มิตินั้น **เข้ารายการสัญญาณขั้น 2** ((a)-(l) ใน 1.1) — มิติที่ไม่มีตัวอักษรกำกับไม่ใช่สัญญาณขั้น 2 โดยตัวเอง

| มิติ | บ่งชี้หลอกเมื่อ | ไม่บ่งชี้เมื่อ |
|---|---|---|
| urgency (รวม sub-type **scarcity**: เหลือคนเดียว/ชิ้นเดียว, คนจองหลายคน, โอนก่อนได้ก่อน) | **ไม่ใช่สัญญาณขั้น 2 โดยตัวเอง** — มีค่าเฉพาะเป็นองค์ประกอบของ (h) "ยืนยันตัวตน/ข้อมูล" คลุมเครือ + เร่ง + ช่องทาง; urgency/scarcity + โอน โดยไม่มีสัญญาณอื่นในรายการขั้น 2 = caution เสมอ (Q1, Q6) — **ไม่มีระดับความเร่งใดที่ยกเป็น danger ด้วยตัวเอง** ("รีบโอนก่อนนะ", "โอนตอนนี้เลย" ก็ยัง caution ถ้าไม่มี (a)-(l)) | โปรโมชั่น, งาน, ครอบครัว; urgency เชิงโปรโมชั่น/scarcity + โอนก่อนส่ง จากผู้ขายไม่รู้จัก โดยไม่มีสัญญาณอื่น = caution ไม่ใช่ danger (Q1, Q6, A3, B7ก) |
| money_request | ขอโอนไปบัญชี/พร้อมเพย์ที่ไม่ใช่ช่องทางทางการ (นิยาม: ช่องทางทางการของสถาบัน = ระบบทะเบียน/bill payment/QR ในนามสถาบัน ไม่ใช่บัญชีที่ให้ในแชท — B4ข), ขอค่าธรรมเนียมเพื่อ "รับ" อะไร (d), **บัญชีบุคคลที่สามใน P2P (ผู้ส่งบอกเองว่าเป็นของแฟน/ญาติ/เพื่อน, ชื่อไม่ตรงผู้ขาย) = สัญญาณโดยลำพัง (b)** (A10, Q2); โอนก่อน/มัดจำ/โอนเต็ม และ "ราคาถูก/ราคาพิเศษ" **ไม่ใช่สัญญาณ** (ไม่มีเกณฑ์ตัวเลขของ "ถูกผิดปกติ" — ถ้าจะเพิ่มต้องกำหนดเกณฑ์ + bump version) | เพื่อนทวงเงิน (มี metadata ยืนยันผู้ส่ง), บิลจริง; **ขอเลขบัญชี/พร้อมเพย์ *ของผู้รับ* เพื่อโอนเงิน *ให้* ผู้รับ** (ผู้ซื้อถามผู้ขาย) — ผู้รับไม่เสียอะไร (A8, Q3); escalation ที่ต้องจับตา: สลิปปลอม / "โอนเกิน ช่วยโอนคืน" / ขอ OTP "เพื่อยืนยันรับเงิน" / ลิงก์รับเงิน → caution/danger |
| amount_mention | — (มิตินี้เป็น metadata: พบจำนวนเงิน ยังไม่รู้ว่าแจ้งหรือขอ) | ค่าจ้าง/ราคาสินค้า/แจ้งยอด — ไม่นับเป็นการขอโดยลำพัง |
| credential_request | **credential ชัด** = OTP / รหัสผ่าน / PIN / รหัสยืนยัน / เลขบัตร — การ **ขอ** ผ่านข้อความ/แชท = สัญญาณโดยลำพัง (a) ไม่ว่าผู้ขออ้างเป็นใคร (แอดมิน, เจ้าหน้าที่, เพื่อน) และ **ไม่ต้องมีเร่ง** (Q4); **คลุมเครือ** = "ยืนยันข้อมูล/ตัวตน" โดยไม่ระบุว่าอะไร — เป็นสัญญาณ (h) เฉพาะเมื่อ + เร่ง + ระบุช่องทางให้ทำ | ระบบ **ส่ง** OTP ให้; ขอเลขบัญชีเพื่อโอนให้ (ดู money_request); "ยืนยันข้อมูล" คลุมเครือไม่มีช่องทาง → นับเป็นการขอ (ขั้น 1) แต่ไม่ใช่สัญญาณ → caution + needs_info ไม่ใช่ danger (B3, C09) |

## 5. Workflow และ field ที่ต้องกรอก

```json
"annotation": {
  "input_form": "direct",
  "cluster_id": "c-0f3a…",
  "labels": [
    {"annotator": "A1", "verdict": "caution", "category": "financial_fraud", "confidence": 3,
     "needs_info": ["seller_identity", "platform_policy"], "notes": ""},
    {"annotator": "A2", "verdict": "danger", "category": "financial_fraud", "confidence": 3,
     "needs_info": [], "notes": "ก้ำกึ่ง"}
  ],
  "final": {"verdict": "caution", "category": "financial_fraud",
            "needs_info": ["seller_identity", "platform_policy"], "resolved_by": "adjudicator"},
  "guideline_version": "1.1"
}
```

field ใหม่ใน v1.1: `input_form` (`"direct"` | `"narrative"` — ขั้น 0), `cluster_id` (ข้อ 0 ของ workflow), `needs_info` (list จากรายการปิดในข้อ 1.3 — ว่างได้; ต้องว่างเมื่อ verdict ≠ caution)

0. **Cluster ก่อน label (B11):** normalize ข้อความ (ตัดตัวยืด นะะะ→นะ, โอนน→โอน, จองง→จอง, สมัก→สมัคร, ตัด PII placeholder) แล้วจัดกลุ่ม near-duplicate → annotator ตัดสิน **ทั้ง cluster ครั้งเดียว** และบันทึก `cluster_id` — ข้อความใน cluster เดียวกัน **ห้าม** ได้ verdict ต่างกัน เว้นแต่มีคำที่เปลี่ยน "การขอ" (เช่น เพิ่ม `line: @id`, เพิ่มเลขบัญชี) ซึ่งต้องแยกเป็น cluster ใหม่; หลักฐาน: judge ให้ template เดียวกันสลับ danger/caution เพราะต่างแค่ typo (43fd054d vs cee5f9f6); การรายงานผลใน thesis นับ **ต่อ template ไม่ใช่ต่อ record**
1. **A1, A2 label อิสระ** — ห้ามดู label ของกันและกัน, ห้ามดู label เดิมจาก source (ซ่อน field `verdict`/`category` เดิมตอน annotate); ให้ดูได้เฉพาะ metadata ที่ใช้ตัดสิน "บริบทตรวจได้" ในขั้น 3 (ที่มา, ผู้ส่งที่ form ระบุ)
2. `confidence` 1-5: 5 = แน่ใจมาก, 3 = ตัดสินได้แต่มีข้อสงสัย, 1 = เดา — confidence ≤ 2 ต้องเขียน `notes`; ถ้าเหตุที่ไม่แน่ใจคือ "ข้อมูลไม่อยู่ในข้อความ" ให้ใช้ `needs_info` แทนการลด confidence (ข้อ 1.3)
3. **ตรงกัน** (verdict และ category) → `final = ค่านั้น`, `resolved_by: "agreement"`; `needs_info` ของ final = union ของ 2 คน **เฉพาะเมื่อ final.verdict = caution** — มิฉะนั้นล้างเป็น `[]` (ใช้กับกรณี adjudicator เลือก danger/safe ทับ caution+needs_info ของอีกคนด้วย ให้สอดคล้องกับกฎ field "needs_info ต้องว่างเมื่อ verdict ≠ caution")
4. **ไม่ตรง** → adjudicator (A3) ตัดสิน, `resolved_by: "adjudicator"`, บันทึกเหตุผลใน `notes` ของ A3
5. รายงาน Cohen's κ แยก verdict / category ทุกรอบ annotate (script: `ml/annotation/agreement.py` — ยังไม่เขียน); `needs_info` ไม่นับใน κ แต่รายงาน % record ที่ set ตรงกัน; รอบแรกของ v1.1 ให้ A2 ตอบ **blind sheet** (`data/annotation/v1.1_calibration_blind.csv` — maintainer export จาก §1.2 เฉพาะคอลัมน์ id / ข้อความ / input_form·metadata·variant ก่อนเริ่ม; อย่างน้อย Q1-Q7 ควรครบ C01-C39) โดย A2 **ต้องไม่เปิดอ่าน §1.2** จนกว่าจะ commit คำตอบ (verdict, category, needs_info, confidence) — บันทึก commit hash ของคำตอบ A2 ไว้ใน notes ของรอบนั้น; agreement ที่วัดหลัง A2 เห็นตารางเป็นการลอก ไม่ใช่หลักฐานว่าการตัดสินของ A1 ทำซ้ำได้
6. κ < 0.7 → ประชุมหา pattern ของความไม่ตรงกัน → แก้ guideline → bump version → re-annotate เฉพาะ record ที่กระทบ

**LLM pre-label:** อนุญาตให้ใช้ LLM ทำ pre-label เพื่อเร่งงาน แต่ (a) annotator ต้องเห็นเป็น "ข้อเสนอ" ไม่ใช่ default ที่กด accept, (b) บันทึกใน `labels` ว่า `annotator: "llm:<model>"` และ **ไม่นับ** เป็น 1 ใน 2 คน, (c) ผลจาก LLM judge/skeptic ใน `ANNOTATION_GUIDELINE_v1.1_proposal.md` เป็นข้อเสนอ ไม่ใช่ ground truth — ทุกข้อถูกคนตัดสินแล้วก่อนเข้า v1.1

## 6. PII

- ก่อนเข้า corpus ทุกข้อความผ่าน `pii_masker.mask_pii(text, "strict")` — annotator จะเห็น `xxx-x-xx5678` / `<URL>` แทนค่าจริง
- ถ้าเจอ PII ที่ masker พลาด (ชื่อจริง, เลขบัญชีรูปแบบแปลก) → **หยุด** แจ้ง maintainer แก้ masker ก่อน ไม่ label ต่อ
- ห้าม copy ข้อความไปวางใน LLM ภายนอกเพื่อช่วยตัดสิน ถ้ายังไม่ mask
- `needs_info: [url]` หมายถึง "ไม่มี URL ในข้อความ" — ถ้า URL ถูก mask เป็น `<URL>` แสดงว่า *มี* URL แต่ annotator เห็นไม่ได้ ให้ดู `source.url`/snapshot (tier A) หรือถาม maintainer ห้ามใส่ needs_info: url เพราะ mask
- `notes`/`needs_info` ห้ามมี PII
